# Redis基础
## 你们项目中的Redis一般运用在什么场景中?有什么作用?
### 一、缓存数据
**网页缓存**
- 当用户频繁访问网页内容时，如新闻网站的文章详情页。这些页面的内容在一段时间内是相对固定的。将网页内容缓存到Redis中，下次用户请求相同页面时，可以直接从Redis中获取数据，大大减少数据库查询和页面渲染的时间。
- ==例如，一个电商网站的商品详情页，包含商品的基本信息、图片、价格等==。这些数据通常不会频繁变更，将其缓存到Redis后，能够在高并发场景下快速响应用户请求，提高用户体验。
**查询结果缓存**
- 对于复杂的数据库查询操作，如涉及多个表的联合查询、带有复杂条件的聚合查询等。如果这些查询结果在短期内不会改变，将其缓存到Redis是个很好的选择。
- 比如，在一个数据分析系统中，需要统计==过去一周内每个用户的活跃天数==。这个查询可能涉及用户行为表、用户表等多个数据表的关联操作。将查询结果缓存到Redis后，后续相同的查询请求可以直接从Redis中获取结果，避免重复执行复杂的数据库查询，减轻数据库的负载。
### 二、会话管理
**用户登录会话**
- 在Web应用中，用户登录后会产生一个会话(Session)。通常==会话信息包括用户ID、登录时间、权限信息等==。将这些会话信息存储在Redis中，可以方便地进行管理。
- 例如，一个在线教育平台，用户登录后，其登录状态、所选课程、学习进度等信息都可以存储在Redis中。当用户在不同页面之间跳转或者刷新页面时，服务器可以快速从Redis中获取用户的会话信息，验证用户身份并提供相应的服务。而且Redis支持设置过期时间，当用户长时间未操作(比如超过30分钟)，会话自动过期，提高系统的安全性。
### 三、消息队列
**异步任务处理**
- 在一些业务场景中，存在一些==不需要立即执行的任务==，==如发送邮件、生成报表等。可以将这些任务的相关信息(如任务类型、任务参数等)放入Redis的列表(List)结构中==，作为一个简单的消息队列。
- 比如，在一个电商系统中，用户下单后需要发送确认邮件和短信。可以将发送邮件和短信的任务信息放入Redis消息队列。后台的任务处理程序可以从Redis队列中取出任务并执行，这样可以将主业务流程和这些辅助任务解耦，提高系统的整体性能和响应速度。
**事件发布与订阅**
- Redis的==发布/订阅(Pub/Sub)==功能可以用于实现事件驱动的架构。例如，在一个社交网络应用中，当用户发布了一条新动态，系统可以将这个事件发布到Redis的频道中。其他关注该用户的用户可以订阅这个频道，当有新动态发布时，订阅者可以及时收到通知并更新自己的页面。
### 四、计数器和排行榜
**计数器**
- 用于==统计网站的访问量、文章的点赞数、视频的播放次数等。Redis的原子操作==(如INCR和DECR命令)可以保证在高并发环境下计数的准确性。
- 例如，一个内容分享网站，需要统计每篇文章的阅读次数。每次用户访问文章时，通过Redis的INCR命令对相应文章的阅读次数计数器进行加1操作。由于Redis的原子性，即使在大量用户同时访问的情况下，阅读次数的统计也不会出现错误。
**排行榜**
- 用于实现各种排行榜功能，如游戏中的玩家==分数排行榜、电商平台的商品销量排行榜==等。可以利用Redis的==有序集合(ZSet)==来存储排行榜数据。
- 比如，在一个在线游戏中，玩家的游戏得分可以存储在Redis的有序集合中。通过ZADD命令添加玩家得分，ZRANGE命令获取排行榜前列的玩家信息。并且可以方便地根据得分的变化实时更新排行榜，满足业务需求。
## Redis为什么这么快?
1. **内存存储**:==Redis是将数据存储在内存当中的，而内存的IO速度比磁盘的IO速度快上几个数量级==，因此Redis很快，同时基于内存也导致其存储空间有限。内存访问一次大概120ns(微秒)，SSD硬盘访问一次50-150us(纳秒)，如果按照访问一次150us来算，性能差距在1000倍。这是因为1us等于1000ns。所以，150微秒是150,000纳秒，而120纳秒只是150微秒的一千分之一。
2. **数据结构**:Redis提供了多种数据结构，5种基础数据结构String、List、Hash、Set、ZSet，3种特殊结构HyperLogLog(布隆过滤器)、Geospatial (地理空间索引)、Bitmaps (位图)，==这些数据结构都是Redis专门优化过的，支持高效的读写操作==。
3. **非阻塞式IO**:==Redis基于IO多路复用实现了非阻塞式IO==，采用IO多路复用技术，并发处理连接。通过epoll模型和自己实现的简单的事件框架，将epoll中的读、写、关闭、连接都转化成了事件，然后利用epoll的多路复用特性，把IO操作时间优化到了极致。
4. **单线程模型**:==Redis把所有主线操作使用单线程模型，将网络IO以及指令读写全部交由一个线程来执行==。这样可以带来==避免线程创建而导致的性能消耗==，==多线程上下文切换而引起的CPU开销，以及避免了多个线程之间的竞争问题==，比如临界区资源的线程安全、锁的申请、释放以及死锁等问题。
## Redis有哪些数据结构?其实现原理是怎样的?
![[Pasted image 20260602205557.png]]
1. **字符串(String)**:字符串是最基本的数据结构，在Redis中以==键值对==的形式存储。字符串类型的值可以包含任何类型的数据，比如整数、浮点数、甚至是二进制数据。Redis的字符串实现基于==简单动态字符串(SDS)==替换了传统字符串，内部有一个len字段记录了字符串长度:实现了O(1)复杂度的strlen操作，并保证了二进制安全性。以及Redis在内部针对区分了多种SDS类型，不同大小的字符串会对应不同的SDS实现，有效的节省内存。
2. **哈希表(Hash)**:哈希表在Redis中以==键值对==的形式存储，其中每个键都对应一个字段和一个值的映射。哈希表==适用于存储对象类型的数据==，比如用户信息、产品信息等。Redis的哈希表实现采用了==类似于Java的HashMap==的数据结构，可以==实现快速的查找、插入和删除操作==。
3. **列表(List)**:列表是一种有序的数据结构，在Redis中以插入==顺序==存储。列表允许重复的值，并且支持在列表的两端进行插入、删除和查找操作，因此可以用于实现队列、栈等数据结构。Redis的列表实现==基于双向链表和压缩列表(当列表长度较短时,Redis自动切换)的数据结构==，具有==高效的插入、删除和索引操作==。
4. **集合(Set)**:集合是一种==无序且不重复==的数据结构，在Redis中用于存储唯一的值。集合支持基本的集合运算，如交集、并集、差集等，并且可以快速地判断一个值是否存在于集合中。Redis的集合实现基于哈希表，可以实现==高效的插入、删除和查找==操作。
5. **有序集合(Sorted Set)**:有序集合是集合的一种扩展，它在每个成员值上关联了一个分数(score)，并且按照分数对成员进行排序。有序集合==适用于需要按照特定顺序访问成员的场景，比如排行榜、优先级队列等==。Redis的有序集合实现基于跳跃表(Skip List)和哈希表，可以实现快速的插入、删除和==按照分数范围进行查找==的操作。
```
ZADD leaderboard 1500 "player_A"
ZADD leaderboard 2300 "player_B"
ZADD leaderboard 1800 "player_C"
ZADD leaderboard 2300 "player_D" 
```
![[Pasted image 20260602214000.png]]
1. **位图(Bitmap)**:位图是一种特殊的数据结构，它以比特(bit)的形式存储数据。在Redis中，位图可以用于记录用户的在线状态、统计用户行为、进行布隆过滤器等。Redis的位图实现使用字节数组来存储位，并提供了一系列位操作命令，如设置位、清除位、计数位等。(==**Bitmap 是用 bit 省内存的神器**：适合大规模二值状态（是/否、有/无、在线/离线）的存储与统计，用 1/8 的内存做同样的事。==)
```
# 用一个 Bitmap 记录所有用户的在线状态
SETBIT online_users 10086 1   # ID 10086 上线
SETBIT online_users 10087 0   # ID 10087 下线
```

2. **HyperLogLog(布隆过滤器)**:HyperLogLog是用于估计基数(集合中不同元素的数量)的算法。它能以极小的内存消耗来估计集合的基数，适合于对大规模数据进行近似统计分析，==例如统计网站的独立访客数或唯一IP数等==。在Redis中，您可以使用HyperLogLog数据结构来执行类似的操作。(==用精度换空间  不保留任何元素，只估算**有多少个**唯一值== )
```
# 记录访问 IP
redis-cli PFADD ips:2026-06-02 192.168.1.1
redis-cli PFADD ips:2026-06-02 192.168.1.2
redis-cli PFADD ips:2026-06-02 192.168.1.1  # 重复 IP，不计入

redis-cli PFCOUNT ips:2026-06-02
# 返回: (integer) 2
```
 **PF** 是 **Philippe Flajolet** 的缩写，HyperLogLog 算法的创始人之一。
3. Geospatial(地理空间索引):Redis的地理空间支持使得您可以将==地理位置信息与键值存储在一起==，并可以基于空间坐标执行范围查询。这允许您在Redis中构建地理信息系统(GIS)应用程序，例如位置服务、附近的商家搜索等。
```
# 1. 添加几个奶茶店的位置
redis-cli GEOADD milktea 116.397 39.916 "喜茶"
redis-cli GEOADD milktea 116.405 39.918 "奈雪"
redis-cli GEOADD milktea 116.380 39.910 "一点点"

# 2. 查"喜茶"和"奈雪"相距多远
redis-cli GEODIST milktea 喜茶 奈雪 km
# 返回: "0.8523"  （约 852 米）

# 3. 查天安门（116.40, 39.90）附近 2 公里有哪些奶茶店
redis-cli GEORADIUS milktea 116.40 39.90 2 km WITHDIST
# 返回:
# 1) "喜茶"
#    1.1) "0.1782"   ← 178 米
# 2) "一点点"
#    2.1) "1.8901"   ← 1.89 公里
```
## Redis宕机数据会丢失吗?
![[Pasted image 20260603162614.png]]
如果Redis没有开启任何的持久化机制，那么数据就会全部丢失，否则只会丢失部分数据，丢失数据的多少取决于采用的持久化配置。
Redis提供了两套持久化机制，RDB和AOF:
RDB会根据设置的情况定期去fork一个子进程，生成当前时间节点数据库的全量快照。如果在RDB快照完成之后出现宕机，那么会丢失掉快照生成期间的全部增量数据，如果在快照还没生成成功的时候宕机，则会丢失掉所有的数据。==（快照模式-Redis 会定期"拍一张照片"，把当前内存里的所有数据保存到硬盘上。）==
AOF则会将每次执行的Redis命令追加到日志文件当中，然后恢复的时候根据日志文件中的指令记录来进行数据的恢复。但是AOF每次命令执行完毕之后数据会先被写入AOF缓存，再写入操作系统缓存，因此刷盘策略决定了==（日志模式-Redis 把每一条写的命令都记到日志文件里。恢复时，就像看录像回放一样，把命令重新执行一遍，数据就回来了。）==
Redis宕机的时候会丢失多少数据。
- Always:每执行一条指令就刷盘一次，最多会丢失一条指令
- Eversec:每秒钟刷盘一次，宕机时最多丢失1s内的数据。
- No:不主动刷盘，由操作系统自己决定，宕机时最多丢失从上一次刷盘到本次刷盘的所有数据

| 策略           | 通俗解释                | 数据安全              | 性能影响       |
| :----------- | :------------------ | :---------------- | :--------- |
| **Always**   | 每执行一条命令，立刻写硬盘       | 最安全，最多丢**1条**命令   | 最慢，每次都要等硬盘 |
| **Everysec** | 每秒统一刷一次盘            | 较安全，最多丢**1秒内**的数据 | 性能适中，常用    |
| **No**       | 完全不管，让操作系统自己决定什么时候写 | 最危险，可能丢**很多**数据   | 最快         |
## Redis的AOF机制是怎么实现的?
![[Pasted image 20260603163419.png]]
AOF(Append Only File)是Redis持久化的一种方式，==通过记录Redis执行的每一条命令，重启后通过重新执行这些命令来恢复数据==。AOF机制确保了数据的完整性和一致性，适用于对数据安全性要求较高的场景。
**AOF机制的工作原理**
AOF文件通过记录Redis执行的每一条命令来保证数据的持久化。当触发AOF重写时(日志越写越臃肿，里面堆满了过时冗余的命令，所以 Redis 会触发**AOF**重写)，==Redis主进程会fork出一个子进程，子进程与主进程共享内存数据==。主进程继续处理新的写入命令，并将这些命令写入AOF缓冲区，同时使用AOF重写缓冲区”保存新数据。==子进程根据内存快照，按照命令合并规则==写入新的AOF文件，每次批量写入硬盘，防止单次刷盘过多造成硬盘阻塞。
**AOF机制的优势和不足**
AOF机制的优势在于其能够确保数据的完整性和一致性，适用于对数据安全性要求较高的场景。然而，==AOF文件随着时间推移会不断增大，可能会影响性能==。此外，==AOF的重写过程需要消耗一定的系统资源。==
## Redis的RDB机制是怎么实现的?
![[Pasted image 20260603164652.png]]
RDB(Redis DataBase)机制是Redis实现数据持久化的一种方式，==主要通过将内存中的数据快照保存到磁盘上==。RDB机制通过定期生成数据快照，将某一时刻的内存数据状态保存为一个RDB文件，从而实现数据的持久化。
1. RDB机制的工作原理
- ==手动触发==:可以通过执行==SAVE 或BGSAVE(**Background Save**)命令来手动触发RDB快照的生成==。SAVE命令会阻塞Redis服务器，直到快照完成，而BGSAVE命令会创建一个子进程来进行快照，主进程可以继续处理其他请求.
- ==自动触发==:通过==配置文件中的save指令==来设置触发条件，例如save 900 1表示900秒内至少有一个键被修改则进行快照。满足条件时，Redis会自动执行BGSAVE命令。
2. RDB机制的实现过程
创建子进程:==Redis父进程通过fork操作创建一个子进程，子进程将内存中的数据写入一个临时文件==。父进程可以继续处理其他请求。
- ==数据写入==:子进程将内存中的数据写入临时文件，完成后替换原有的RDB文件。
- ==完成信号==:子进程完成快照后发送信号给父进程，==父进程更新相关统计信息==。
3. RDB机制的优缺点
优点:
- ==简单高效==:RDB机制实现简单，适合大规模数据的备份和恢复，恢复速度较快。
- ==适合备份==:通过快照的方式保存数据，适合定期备份和数据分析。
缺点:
==数据丢失风险==:RDB机制==可能会丢失最后一次快照之后的数据==，不适合对数据丢失要求严格的场景
4. RDB机制的应用场景
RDB机制==适用于需要快速备份和恢复大规模数据的场景==，例如数据库的定期备份和灾难恢复。由于其简单高效的特性，RDB机制在需要高性能和数据快速恢复的场景中尤为适用

## 什么是布隆过滤器?
![[Pasted image 20260603172913.png]]
==布隆过滤器（Bloom Filter）是一种空间效率极高的数据结构==。用于快速判断一个元素是否在集合中
### **布隆过滤器的工作原理**
布隆过滤器的核心思想是使用**多个哈希函数**(Hash Functions)和一个**位数组（Bit Array）**。其操作过程如下：
- ==插入元素==:当插入一个元素时，布隆过滤器会==使用多个不同的哈希函数对该元素进行哈希计算，得到多个哈希值（位置索引），并将这些哈希值对应的位数组位置设置为 1==。 例如，一个元素经过 3 个哈希函数后，得到了 3 个不同的位置，布隆过滤器就在这 3 个位置上将位数组的值设为 1。
- 查询元素:查询某个元素时，布隆过滤器会==使用相同的哈希函数对该元素进行哈希计算，得到多个位置。如果所有这些位置的位都为 1，则布隆过滤器认为这个元素可能存在；如果任意一个位置的位为 0，则可以确定这个元素一定不存在。==
### **特点**
- **可能存在误判**：布隆过滤器有可能出现误判，查询一个不存在的元素时，==有小概率会因为位数组中的某些位被其他元素设为 `1`==，而误认为这个元素存在。
- **不会漏判**：==如果某个元素不存在，布隆过滤器一定不会误判其存在==，即布隆过滤器查询某个元素是否存在时，若判断不存在，结果是可靠的。
所以它常用在缓存穿透场景里:请求进来先过布隆过滤器，如果判断一定不存在，就没必要再打Redis和数据库。
### HyperLogLog和布隆过滤器(易混淆)
HyperLogLog和布隆过滤器(Bloom Filter)属于同一类概率型数据结构（Probabilistic Data Structures），核心思想都是**用可控的精度损失来换取极大的空间效率**，但解决的问题不同。
- 先用 **Bloom Filter** 判断"这个用户ID是否已注册过？"
- 再用 **HyperLogLog** 统计"今天有多少独立访客（UV）？"

# Redis常见面试题&详解
## 如何解决缓存击穿
![[Pasted image 20260603204544.png]]
==缓存击穿==说的是==某个热点key 刚好失效，大量请求同时打进来，结果都绕过Redis去查数据库，数据库压力瞬间升高。==
解决思路一般有三类。
- 第一是==加互斥锁，只让一个线程去查数据库并重建缓存，其他线程等结果==;这里最好做双重检查，拿到锁后再看一次缓存，避免重复查库。
- 第二是==热点数据提前预热==，比==如大促前把核心商品信息提前放进Redis==。
- 第三是==热点key逻辑不过期==，也就是==缓存里不直接设置短TTL(**Time To Live**)，而是在value里维护过期时间==，由后台异步刷新。
**混淆解释**
传统 TTL(Redis 自动管理):Redis 内部有个定时器，300 秒后自动把这条 Key 删掉。你的业务代码完全不知道它什么时候过期。
逻辑不过期(过期时间写在 Value 里):Redis 认为这条数据永远有效，但你的==业务代码读取后，自己判断 `expire_at` 是否到期。==
```
# Redis 存储结构
Key:    "product:10086"
Value:  {
          "data": {name: "iPhone", price: 5999},   ← 真正的业务数据
          "expire_at": 1717420800,                   ← 过期时间戳（秒）
          "version": 1                               ← 可选：版本号
        }
TTL:    永不过期（或设个兜底 30 天）                   ← Redis 不管这条数据的生死
```
## 如何解决缓存穿透
![[Pasted image 20260603211143.png]]
==缓存穿透==是指==查询一个 **不存在的数据**，导致请求直接穿透缓存层，直接访问数据库==。由于==数据库中也不存在该数据，因此每次请求都会绕过缓存，直接访问数据库==，从而导致数据库压力过大。
### 空对象值缓存
![[Pasted image 20260603212809.png]]
==当查询结果为空时，也将结果进行缓存==，但是设置一个较短的过期时间。这样在接下来的一段时间内，如果再次请求相同的数据，就可以直接从缓存中获取，而不是再次访问数据库。这种方式是比较简单的一种实现方案，可以很好解决缓存穿透问题，但是会存在一些==弊端==。那就是当==短时间内存在大量恶意请求，缓存系统会存在大量的内存占用==。如果要解决这种海量恶意请求带来的内存占用问题，需要搭配一套风控系统，对用户请求缓存不存在数据进行统计，进而封禁用户。整体设计就较为复杂，不推荐使用。
### 使用锁
当请求发现==缓存不存在==时，可以使用==锁机制==来避免多个相同的请求同时访问数据库，==只让一个请求去加载数据，其他请求等待。==
这种方式可以解决数据库压力过大问题，如果会==出现“误杀”现象==，==那就是如果缓存中不存在但是数据库存在这种情况==，也会等待获取锁，用户等待时间过长，不推荐使用。、
### 布隆过滤器
![[Pasted image 20260603212758.png]]
==布隆过滤器==是一种数据结构，==可以用于判断一个元素是否存在于一个集合中==。当业务系统有查询请求的时候，==首先去 BloomFilter 中查询该 key 是否存在。若不存在，则说明数据库中也不存在该数据，因此缓存都不要查了，直接返回 null( **初始化时**：把所有数据库已有的 key 都写入 BloomFilter)==。若存在，则继续执行后续的流程，先前往缓存中查询，缓存中没有的话再前往数据库中的查询。
### 组合方案
上面的这些方案或多或少都会有些问题，应该用三者进行组合用来解决缓存穿透问题。==如果说缓存不存在，那么就通过布隆过滤器进行初步筛选，然后判断是否存在缓存空值，如果存在直接返回失败。如果不存在缓存空值，使用锁机制避免多个相同请求同时访问数据库。最后，如果请求数据库为空，那么将为空的Key进行空对象值缓存。==
请求布隆过滤器和缓存空值判断会向Redis发起两次网络IO，如果想优化的话，可以使用管道或者Lua命令来提高性能。详情参考: 如何提升Redis批量访问性能?(opensnew window)
## 如何解决缓存雪崩
![[Pasted image 20260603213320.png]]
缓存雪崩是应用系统指在==某个时间点上，缓存中的大部分数据同时失效==，==导致大量的请求直接访问底层数据库或后端服务==，从而造成数据库负载剧增，甚至导致数据库崩溃的情况。通常情况下，缓存中的数据会设置不同的过期时间，以避免同时失效的情况。然而，如果某个不可控的事件导致了大量缓存同时失效，就会出现缓存雪崩。需要从以下几个方面去解决缓存雪崩问题:
1. ==热点数据永不过期==:对于一些热点数据，可以设置永不过期，以保证这部分数据始终在缓存中可用。
2. ==合理设置缓存失效时间==:避免所有缓存在同一时间点失效，可以采用随机分布的方式设置缓存失效时间，或者使用带有随机偏移的失效时间。
3. ==缓存预热==:在系统启动时，将热门数据预先加载到缓存中，避免在高并发时出现缓存失效问题。
4. ==使用本地锁或者分布式锁==:可以使用锁机制来避免多个相同的请求同时访问数据库，只让一个请求去加载数据，其他请求等待。
通过以上几种方案组合使用，可以一定程度上减少缓存雪崩的可能性。
